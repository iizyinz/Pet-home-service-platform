# 一、项目概述

## 1.1 背景与问题

养宠人群在临时出差、加班、旅行等场景下存在真实的上门喂养、遛狗、洗护、寄养、基础体检等服务需求。传统找人方式存在三大痛点：一是渠道分散（问朋友欠人情、陌生人不可信）；二是服务人员资质不透明（无法判断专业能力与认证）；三是服务质量无保障（服务过程不可追溯、出问题难以定责）。

本系统的核心思路是「把上门服务做成一笔可查、可管、可追责的工单」：先建立宠物档案，再按区域与擅长品种匹配服务人员，在线预约并余额支付，服务人员接单上门并全程反馈服务过程，用户确认完成后评价，平台沉淀信誉与运营数据，形成多方协作、状态可控的业务闭环。

## 1.2 产品目标

- 业务目标：为宠物主提供可信、可追溯、可评价的一站式上门宠物服务预约平台。
- 体验目标：下单—接单—履约—确认—评价全链路线上化，服务过程可视、结果可评、纠纷可查。
- 运营目标：为平台方提供订单、收入、人员、评价的全维度数据看板与信誉治理能力。
- 技术目标：多角色协同 + 订单状态机 + 实时通信 + AI 问答 + 数据可视化，体现工程复杂度与可维护性。

## 1.3 范围界定

### 1.3.1 范围内（In Scope）

- 用户端小程序：宠物档案、地址、服务浏览、服务人员筛选、预约下单、余额支付、订单跟踪、进度查看、确认完成、评价、收藏、即时聊天、AI 宠物问答、个人中心。
- 服务人员端小程序（同一 App 内工作台）：待处理订单、接单/开始/完成、排期日历、服务进度发布、个人资料与可服务项目、评分与累计接单。
- 管理端 Web：用户/服务人员/服务项目/服务类型/服务区域/宠物档案/订单/评价/轮播图/公告/通知/余额流水/操作日志管理，数据看板、评价词云。

### 1.3.2 范围外（Out of Scope）

- 真实第三方在线支付网关（本项目以平台内部「余额账户 + 充值流水」模拟支付与退款，不接入微信/支付宝真实扣款）。
- 服务人员定位导航、实时位置轨迹、上门打卡 GPS 核验等 LBS 深水区能力（预留字段与扩展点）。
- 宠物医疗资质审核对接、保险理赔等线下强合规环节。
- 内容社区、宠物电商交易（首页「优惠专区」等营销位仅作展示占位，不含下单）。

> 注：若后续接入真实支付或 LBS，本 PRD 的余额流水表与订单表已预留 channel、经纬度等扩展字段，无需重构主链路。

# 二、用户角色与权限

## 2.1 角色定义

系统包含三类业务角色，围绕同一张订单协同。角色之间权限隔离、视角不同，通过统一登录入口按角色路由到各自工作台。

### 2.1.1 用户（宠物主）

- 维护宠物档案（品种、年龄、体重、健康信息、特殊需求）与上门地址。
- 浏览服务项目、按服务类型/区域/擅长品种筛选服务人员、收藏服务人员。
- 在线预约并余额支付下单、查看订单与服务进度、确认完成并提交评价。
- 与服务人员在线私聊，使用 AI 宠物问答。
- 个人中心管理余额（充值、余额变动记录）、我的评价、我的收藏、退出登录。

### 2.1.2 服务人员

- 工作台查看待处理订单，接单、开始服务、标记完成并记录实际服务时间。
- 按订单发布服务过程反馈（标题 + 图片 + 服务时间）。
- 查看服务排期日历、维护个人资料与可服务项目、查看评分与累计接单。
- 与用户在线私聊，接收评价、订单状态变更等系统通知。

### 2.1.3 管理员

- 维护用户、服务人员、服务项目、服务类型、服务区域、宠物档案等主数据。
- 管理订单、评价、轮播图、公告、通知与余额流水；审核服务人员资质。
- 查看操作日志（审计），并通过数据看板与词云分析经营与口碑数据。

# 三、核心业务流程

## 3.1 订单主流程（正向）

一笔订单从创建到完成的核心路径如下，全过程受订单状态机控制，每步动作前先校验当前状态是否允许。

```
用户浏览服务/人员 → 选择宠物+服务项目+服务师+上门地址+预约时间 → 提交预约(生成待确认订单,校验并扣余额) → 服务师接单(→已确认) → 服务师开始服务(→服务中,可多次发布进度) → 服务师标记完成(→待确认完成,记录实际时间) → 用户确认完成(→已完成) → 用户提交评价(一单一评,重算信誉,推送通知)
```

## 3.2 逆向与异常流程

- 取消订单：用户在服务开始前可取消，系统退回订单金额并生成退款流水，订单进入「已取消」并单独归集，不再参与正常列表统计。
- 拒单/超时未接：服务师拒单或长时间未接单（建议 24h 超时），订单退回并释放余额、通知用户改选或取消。
- 完成但用户不确认：用户超时（建议 72h）未确认，系统按业务规则自动流转为已完成并允许评价，避免订单长期滞留。
- 退款争议：管理员可在订单详情进行运营干预（退款/关闭），操作需写入操作日志。

## 3.3 消息与通知流程

- 即时聊天：发送方消息先落库，再判断接收方是否在线；在线则通过 WebSocket 定向推送，离线则留存待接收方拉取历史；会话列表展示最新一条与未读数。
- 系统通知：订单状态变更（新订单、接单、完成、取消）、收到评价等事件生成站内通知，推送到对应角色的通知中心。

## 3.4 AI 宠物问答流程

用户提问 → 服务端组装上下文（系统提示词 + 该会话历史消息 + 当前问题）→ 调用大模型（DeepSeek 等，OpenAI 兼容接口）→ 以 SSE 流式返回 token → 前端逐字渲染 → 会话与消息落库（保存 role、内容、时间）。会话按时间排序，支持新建会话、查看历史、继续追问。

# 四、订单状态机设计【强制】

## 4.1 状态定义

| 状态码(status) | 名称 | 含义 | 可执行动作 |

| --- | --- | --- | --- |

| PENDING_CONFIRM | 待确认 | 用户已下单并扣款，等待服务师接单 | 服务师:接单/拒单；用户:取消 |

| CONFIRMED | 已确认 | 服务师已接单，等待上门 | 服务师:开始服务；用户:取消 |

| SERVING | 服务中 | 服务师已开始服务，可发布进度 | 服务师:标记完成；查看进度 |

| PENDING_SETTLE | 待确认完成 | 服务师标记完成并记录实际时间，等待用户确认 | 用户:确认完成 |

| COMPLETED | 已完成 | 用户确认完成，可评价 | 用户:提交评价(一单一评) |

| CANCELLED | 已取消 | 用户取消/拒单/退款，订单终止 | 仅查看；单独归集 |

## 4.2 允许的流转（状态转移表）

| 当前状态 | 动作 | 目标状态 | 触发角色 | 校验/副作用 |

| --- | --- | --- | --- | --- |

| PENDING_CONFIRM | accept 接单 | CONFIRMED | 服务人员 | 订单归属校验；通知用户 |

| PENDING_CONFIRM | reject 拒单 | CANCELLED | 服务人员 | 退款+写退款流水；通知用户 |

| PENDING_CONFIRM | cancel 取消 | CANCELLED | 用户 | 退款+写退款流水；通知服务师 |

| PENDING_CONFIRM | timeout 超时未接 | CANCELLED | 系统(定时) | 退款+流水；通知双方 |

| CONFIRMED | start 开始服务 | SERVING | 服务人员 | 记录开始时间；通知用户 |

| CONFIRMED | cancel 取消 | CANCELLED | 用户 | 退款+流水 |

| SERVING | feedback 发布进度 | SERVING | 服务人员 | 新增进度记录(不改状态)；可推送 |

| SERVING | finish 标记完成 | PENDING_SETTLE | 服务人员 | 记录实际完成时间；通知用户确认 |

| PENDING_SETTLE | confirm 确认完成 | COMPLETED | 用户 | 通知服务师；开放评价入口 |

| PENDING_SETTLE | auto_confirm 超时 | COMPLETED | 系统(定时) | 防滞留；开放评价 |

```
非法流转一律拒绝：对不在上表内的 (当前状态, 动作) 组合，接口返回业务错误码并提示「订单当前状态不允许此操作」；状态更新与副作用（退款、流水、通知、信誉重算）必须在同一事务内完成。
```

# 五、功能需求（用户端小程序）

以下按模块给出功能点、业务规则与验收要点。开发实现对应 uni-app（微信小程序）页面，接口见第九章。

## 5.1 登录与账号

- 账号密码 + 图形验证码登录；支持记住我、忘记密码（重置）。
- 新用户注册后默认分配对应角色（用户/服务人员），管理端账号由系统预置。
- 登录成功签发 JWT（含 userId、role、过期时间），前端存本地并在请求头携带。

## 5.2 首页

- 轮播图（后台可配）、服务分类入口（宠物训练/洗护/遛弯/寄养/医疗等）、AI 宠物顾问入口、通知公告列表（点击查看明细）、推荐服务师列表（评分/从业年限/接单量/认证标识）。
- 底部 Tab：首页 / 服务 / 订单 / 消息 / 我的。

## 5.3 服务浏览与筛选

- 按服务类型、关键词搜索服务项目；列表展示名称、分类、价格、时长、适用品种、查看详情。
- 服务详情展示价格、时长、适用品种列表、注意事项；提供「立即预约」入口。
- 服务人员列表按区域、擅长品种筛选；服务人员详情展示评分、从业年限、累计接单、认证状态、资质证书、个人简介、服务评价，支持收藏与在线私聊。

## 5.4 预约下单与余额支付

- 预约表单：选择宠物、服务项目、服务师、上门地址、预约日期时间、备注。
- 【强制】提交时校验用户余额 ≥ 订单金额，余额不足提示充值；下单成功后生成 SO 开头订单号、同步扣减余额并写入消费流水（金额、余额快照、类型=消费、关联订单）。
- 价格来源：订单金额 = 所选服务项目单价（按次计费），V1 不含优惠券/折扣计算逻辑（预留字段）。

## 5.5 订单中心

- 按状态分页查看订单（全部/待确认/已确认/服务中/待确认完成/已完成/已取消）。
- 订单卡片展示订单号、服务项目、宠物、服务师、预约时间、金额、可操作按钮（私信/取消/确认完成/详情）。
- 订单详情展示客户与服务的完整信息快照，可查看服务进度（未读标记，查看后记录阅读时间与已读状态）。

## 5.6 评价

- 【强制】评价仅限「已完成」订单，且一单一评（重复提交拒绝）。
- 评价内容：星级评分（1–5）、文字内容、可选图片。
- 保存成功后触发：重算服务人员平均评分与累计完成订单数，并向服务人员推送评价通知。

## 5.7 即时聊天（用户↔服务人员）

- 会话列表：展示每个聊天对象的最新一条消息、时间、未读数。
- 聊天详情：历史消息分页加载、发送文本/图片消息，在线即时收发（WebSocket），离线落库可拉取。

## 5.8 AI 宠物顾问

- 提供常见问题快捷入口（如「如何给猫咪洗澡」「狗狗不吃东西怎么办」「疫苗时间表」「定点排便训练」）。
- 流式回答（SSE），会话保存并可回看历史；提示词与知识范围聚焦宠物护理、健康、饮食、训练、品种。

## 5.9 个人中心

- 个人信息完善（头像、昵称、手机号等）、宠物档案管理、地址管理、我的评价、我的收藏。
- 我的余额：展示当前余额、充值入口、余额变动记录（消费/充值，含时间、变动金额、变动后余额）。

# 六、功能需求（服务人员端工作台）

服务人员端与用户端在同一小程序内，登录后按 role 进入工作台。核心是围绕「本人相关订单」的履约操作。

## 6.1 工作台首页

- 概览：待接单数、进行中数、今日完成数、累计完成订单数、累计收入、综合评分、认证状态。
- 待办订单列表（待确认优先），点击进入订单详情执行接单等操作。

## 6.2 订单处理

- 订单按状态分页（全部/待接单/已确认/服务中/待确认完成/已完成/已取消）。
- 【强制】接单、开始服务、标记完成均走状态机接口并记录时间戳；标记完成时录入实际服务开始/结束时间。
- 订单详情展示客户信息、联系电话、服务地址、宠物信息、服务项目与金额、订单编号，可私信客户或接单。

## 6.3 服务过程反馈【强制】

- 针对「服务中」订单发布进度：标题 + 图片(可多张) + 服务时间/说明。
- 进度列表按时间倒序；用户端查看后标记已读并记录阅读时间。

## 6.4 服务排期

- 月历视图，点击某天展示当日订单排期（时间、项目、宠物、客户、地址、状态）。

## 6.5 个人中心

- 维护个人资料（简介、擅长品种、资质证书、联系电话）、可服务区域、可提供的服务项目。

# 八、关键技术机制（全栈实现约束）

## 8.1 余额支付与退款

- 余额模型：用户账户维护 balance；资金变动一律通过流水表记录，不允许只改余额不留痕。
- 下单扣款：校验 balance ≥ amount，扣减并插入流水（type=CONSUME），生成 SO 订单号；校验与扣减需原子化（行级锁/乐观锁）防并发超扣。
- 退款：取消/拒单/超时退回，balance 增加并插入流水（type=REFUND），与订单状态流转同事务。
- 充值：balance 增加并插入流水（type=RECHARGE）；本项目充值为模拟，不接真实支付网关。

## 8.2 订单状态机与事务

- 所有状态变更集中在统一的状态流转服务中处理，禁止各业务散点改 status 字段。
- 状态更新 + 资金流水 + 通知 + 信誉重算等同事务写入；失败整体回滚。
- 定时任务：超时未接自动取消退款、待确认完成超时自动确认，需幂等。

## 8.3 服务过程反馈与已读

- 进度与订单 1:N，字段含标题、图片(JSON/数组)、服务时间、创建时间。
- 已读标记：记录每订单最后阅读时间与是否已读（可按进度粒度或订单粒度，V1 采用订单粒度 latest_read_at）。

## 8.4 即时聊天（WebSocket）

- 消息先落库（sender/receiver/content/type/会话/时间），再判断接收方在线状态；在线则定向推送，离线留存。
- 连接鉴权：WebSocket 握手携带 JWT 校验身份；维护 userId→连接 的在线映射，支持多端与断线重连。
- 会话列表按 (参与者对) 聚合最新一条与未读数。

## 8.5 AI 宠物问答（SSE 流式）

- 会话表 + 消息表（role=system/user/assistant）。组装上下文 = 系统提示词 + 历史消息 + 当前问题，调用大模型 OpenAI 兼容接口。
- 服务端以 SSE 逐块下发（Content-Type: text/event-stream），前端 EventSource 增量渲染；回答完整后落 assistant 消息。
- 需做超时/失败兜底：模型异常时返回错误提示且不污染会话历史。

## 8.6 评价与信誉统计

- 一单一评（订单+评价者唯一约束）；仅已完成订单可评。
- 评价保存后重算服务人员 avg_rating（基于全部评价的加权平均，精度 1 位小数）与 completed_count（累计已完成订单数），并推送通知；重算走聚合 SQL，避免应用层重复累加漂移。

## 8.7 词云与运营分析

- 词云：取评价文本 → HanLP 分词与词性标注 → 过滤停用词与无效词性 → 按词频取 Top 80 → 前端词云渲染。
- 看板：统计走聚合查询/物化视图，近 N 天趋势按日 group by；排行按服务项目/服务人员聚合排序。

# 十一、非功能需求

## 11.1 性能

- 核心接口 P95 响应时间 ≤ 500ms（列表类 ≤ 800ms）；下单扣款接口 ≤ 1s 且强一致。
- WebSocket 消息端到端投递延迟 ≤ 200ms（在线场景）。
- AI 问答首 token ≤ 3s，流式无明显卡顿；并发问答走异步/限流保护。
- 数据看板聚合查询 ≤ 2s，可对统计类做缓存或定时物化。

## 11.2 安全

- JWT 鉴权 + 角色权限隔离，接口按登录者归属过滤数据，防越权（水平/垂直）。
- 密码 BCrypt 存储，登录失败次数限制与验证码防爆破，敏感手机号展示脱敏。
- 下单/退款等资金操作幂等 + 事务 + 并发控制（乐观锁/唯一约束），防重复扣款与超扣。
- 管理端关键操作写入操作日志（审计可追溯）；输入校验与参数化查询防 SQL 注入，XSS 过滤。

## 11.3 可用性 / 兼容 / 数据

- 小程序端适配主流机型与微信基础库；管理端支持 Chrome/Edge 等现代浏览器。
- 上传文件（图片/资质）走对象存储或本地目录，做大小/类型校验；聊天与进度图片支持懒加载。
- 关键业务（订单、流水、评价）逻辑删除或保留快照，服务项目/价格变更不影响历史订单快照一致性。
- 时间统一 GMT+8；日志、异常统一格式并可定位 traceId。

## 11.4 可维护性

- 后端严格分层 Controller / Service / Mapper（MyBatis），公共能力（鉴权、审计、异常、结果封装）以拦截器/AOP 收敛。
- 接口与字段命名遵循本 PRD 约定，前后端以接口文档为契约；新增能力通过扩展字段而非改主链路。

# 十三、验收标准（关键 Given/When/Then）

以下为不可省略的核心验收项，供测试与 AI 编程工具自检。

### AC-01 下单扣款

```
Given 用户余额 100 元,服务项目单价 158 元; When 提交预约; Then 拦截并提示余额不足,不生成订单、不产生流水。
```

### AC-02 下单成功

```
Given 余额充足且已选宠物/服务/服务师/地址/时间; When 提交预约; Then 生成 SO 订单号,status=PENDING_CONFIRM,balance 减少,写入一条 type=CONSUME 流水(balance_after 正确)。
```

### AC-03 状态机合法性

```
Given 订单 status=COMPLETED; When 服务师调用 start; Then 拒绝并返回「当前状态不允许此操作」,status 不变。
```

### AC-04 取消退款

```
Given 订单 status=PENDING_CONFIRM; When 用户取消; Then status=CANCELLED,balance 增加,写入 type=REFUND 流水,通知服务师,订单在列表单独归集。
```

### AC-05 服务反馈已读

```
Given 服务师对 SERVING 订单发布进度; When 用户进入订单详情查看进度; Then 标记已读并记录阅读时间,未读计数归零。
```

### AC-06 一单一评与信誉重算

```
Given 订单 status=COMPLETED 且未评价; When 用户提交 5 星评价; Then 保存成功,服务师 avg_rating 与 completed_count 按全部评价重算并更新,推送评价通知; 重复提交被拒绝; 非已完成订单不可评价。
```

### AC-07 即时聊天

```
Given 接收方在线; When 发送方发消息; Then 消息先落库,再通过 WebSocket 定向推送给接收方; 接收方离线时落库保留,再次上线可拉取历史; 会话列表未读数正确。
```

### AC-08 AI 流式问答

```
Given 存在会话历史; When 用户提问; Then 服务端组装系统提示词+历史+当前问题调用模型,SSE 逐块返回,前端增量渲染,完成后落 assistant 消息; 模型异常返回错误且不写入会话。
```

### AC-09 越权防护

```
Given 服务师 A; When 操作非本人订单 B 的状态接口; Then 返回 403,不产生任何状态或资金变更。
```

### AC-10 词云与看板

```
Given 存在多条评价文本; When 请求词云/看板; Then 词云按 HanLP 分词去停用词取 Top80; 看板指标(订单/收入/用户/服务师/宠物/满意率/状态分布/趋势/排行)与数据库聚合结果一致。
```

# 十四、开发落地建议与里程碑

## 14.1 建议实施顺序

- M1 基础设施：工程骨架、登录鉴权(JWT)、统一响应与异常、AOP 审计、角色路由。
- M2 主数据：宠物/地址/服务类型/区域/项目/服务人员档案与资质审核。
- M3 交易闭环：下单+余额支付(流水)+订单状态机+定时超时；这是核心，须先保证事务与幂等。
- M4 履约协同：服务反馈+已读、服务人员工作台、排期。
- M5 沟通智能：WebSocket 聊天、AI 问答(SSE)。
- M6 口碑分析：评价+信誉重算、词云、ECharts 数据看板、公告/轮播/通知。

## 14.2 给 AI 编程工具的执行提示

- 逐模块实现，优先打通 M1–M3 交易主链路并跑通状态机与资金流事务，再叠加实时与智能能力。
- 实现状态机时严格对照第四章转移表，禁止散点修改 status；所有写接口加归属校验。
- 金额/流水/信誉重算须防并发（乐观锁、唯一约束、聚合 SQL），并以 AC 用例自测。
- 前端按第九章字段与第十章接口为契约联调，接口文档与类型定义保持同步。
